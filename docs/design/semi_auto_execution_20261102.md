# 半自动执行系统设计（V5 生产，人机协同）

- 版本：v0.1 设计稿
- 日期：2026-11-02
- 状态：设计，不改生产、不接券商、不下单
- 适用范围：V5 生产信号（V4 影子仅展示，不产生执行票）

## 1. 问题定义

当前链路是：

```text
14:50 live_signal 生成信号
      ↓
网页/Bark 提示
      ↓
用户自己打开易淘金、手工下单
      ↓
用户回网页登记实际成交
```

根因不是“信号不准”，而是**执行环节没有状态机**：

- 信号生成后没有明确的执行窗口、截止时间、升级路径；
- 用户忘记后，pending 可以挂 11 天（2026-10-22 案例）；
- 没有“同一天 14:50”和“次日 09:25”两个执行窗口的区分；
- 没有“未执行”的终态和漏单复盘，忘记成本不可见；
- 没有 ticket、提醒记录、实际成交与模型计划的偏差统计。

目标：在不接券商、不存密码、不做 RPA 的前提下，把“忘记”从人的问题变成系统可观测、可提醒、可复盘的状态机。

非目标：

- 不自动下单；
- 不接入 QMT/PTrade；
- 不保存券商密码/验证码；
- 不修改 V5 选品/风控参数；
- 不替用户判断是否应该交易。

## 2. 设计原则

1. **人机协同**：系统准备订单票和提醒，用户执行，系统对账。
2. **每个信号都有 ticket**：没有 ticket 的信号不允许进入执行流程。
3. **每个 ticket 都有 deadline**：同日 15:00 和次日 09:30 两个窗口。
4. **提醒可升级、可停止、可去重**：确认/跳过后立即停止；同一窗口不重复轰炸。
5. **失败关闭**：数据过期、行情缺失、服务异常时不生成 ticket，只发异常告警。
6. **幂等**：同一 `decision_id` 不生成第二张 ticket；确认/跳过重复提交不重复记账。
7. **可审计**：状态变化、提醒、确认、跳过、实际成交全部留痕。
8. **移动优先**：手机上 30 秒内能完成“看一眼、复制、确认/跳过”。

## 3. 用户旅程与双执行窗口

V5 回测口径是 T 收盘信号、下一交易日开盘成交；生产实际是 14:50 信号、当日收盘前执行。半自动设计同时支持两个窗口：

```text
T 日 14:45  预提醒：今天可能有信号，准备易淘金
T 日 14:50  正式信号 + 订单票 + Bark
T 日 14:55  第一次升级（未处理）
T 日 15:02  第二次升级（未处理，接近收盘）
T 日 15:10  同日窗口关闭；保留 pending，进入次日开盘窗口
T+1 09:15   盘前提醒：昨日信号仍可开盘执行
T+1 09:25  第二次盘前提醒（集合竞价前后）
T+1 09:30  开盘窗口
T+1 09:35  仍未处理 → EXPIRED_UNRESOLVED，日报记漏单
```

规则：

- **同日窗口**：14:50–15:00，优先按生产 14:50 口径执行。
- **次日窗口**：T+1 09:25–09:30，按 V5 回测的 next-open 口径执行；不假装是 14:50 成交。
- 两个窗口都错过，才进入 `EXPIRED_UNRESOLVED`；不自动跳过。
- 非交易日、节假日、数据异常：不生成 ticket。
- 用户确认/跳过后，所有后续提醒立即取消。

## 4. 状态机

```text
DRAFT
  │ 生成 ticket、校验数据
  ▼
PENDING ──确认全部成交──▶ CONFIRMED
  │  │
  │  ├──部分成交──▶ PARTIAL ──补齐──▶ CONFIRMED
  │  ├──用户跳过──▶ SKIPPED
  │  ├──同日窗口关闭──▶ PENDING（保留，进入次日窗口）
  │  ├──次日窗口关闭──▶ EXPIRED_UNRESOLVED
  │  └──数据/服务异常──▶ BLOCKED
  │
  └──新信号到达且旧 ticket 未决──▶ 不自动覆盖，提示先处理旧 ticket
```

状态定义：

| 状态 | 含义 | 是否阻塞新信号 | 后续动作 |
| --- | --- | --- | --- |
| `DRAFT` | 已生成，未通知 | 否 | 校验后转 PENDING |
| `PENDING` | 等待用户执行 | **是** | 提醒/确认/跳过 |
| `PARTIAL` | 部分腿已成交 | **是** | 补齐或说明 |
| `CONFIRMED` | 全部腿已按实际成交登记 | 否 | 对账/复盘 |
| `SKIPPED` | 用户明确不交易 | 否 | 记录原因 |
| `EXPIRED_UNRESOLVED` | 两个窗口都错过 | **是** | 用户补登/跳过/标记漏单 |
| `BLOCKED` | 数据/服务异常，未生成可执行票 | 否 | 修复后重跑 |
| `CANCELLED` | 系统撤销（如池变更） | 否 | 审计 |

关键约束：

- `PENDING`/`PARTIAL`/`EXPIRED_UNRESOLVED` 都阻塞新订单，防止“旧单没处理，新单又来了”。
- 不允许系统自动把 `PENDING` 改成 `SKIPPED`；跳过必须由用户明确操作。
- 同一 `decision_id` 只能有一张 ticket；重复生成返回已有 ticket。
- 确认接口幂等键 = `ticket_id + leg_id + idempotency_key`。

## 6. 提醒系统

### 6.1 提醒矩阵

| 时间 | 条件 | 内容 | Bark level | 是否重复 |
| --- | --- | --- | --- | --- |
| T 14:45 | 交易日，且今天是 5 日网格日或已有 1/2 确认候选 | “今日可能有 V5 信号，准备易淘金” | active | 每日最多 1 次 |
| T 14:50 | `run_daily` 生成 ticket | 完整订单票（由 live_signal 发送） | active | 1 次 |
| T 14:55 | 仍 PENDING | “还有 5 分钟到同日窗口” | timeSensitive | 1 次 |
| T 15:02 | 仍 PENDING | “同日窗口即将关闭，是否已成交？” | timeSensitive | 1 次 |
| T 15:10 | 仍 PENDING | “同日窗口已关闭；明日 09:25 可开盘执行” | active | 1 次 |
| T+1 09:15 | 仍 PENDING | “昨日信号仍可开盘执行” | active | 1 次 |
| T+1 09:25 | 仍 PENDING | “5 分钟后开盘，最后窗口” | timeSensitive | 1 次 |
| T+1 09:35 | 仍 PENDING | “已错过两个窗口，请补登/跳过” | timeSensitive | 1 次 |

### 6.2 提醒规则

- 只在交易日、且存在 `PENDING`/`PARTIAL` 时发送。
- 用户确认/跳过/补登后，立即取消后续提醒。
- 同一 `dedupe_key` 只发一次；cron 重跑不重复。
- Bark 失败：指数退避重试 3 次（1s/5s/30s），再发邮件/备用 webhook，写 `notify_failures.log`。
- 22:00–08:00 不发送，09:15 盘前除外。
- 内容只含代码/份额/价格/窗口，不含账号密码。
- 通知里附网页深链，点开直接到 ticket。

### 6.3 提醒调度

新增 `scripts/remind_pending.py`，由 cron 在固定时间调用：

```cron
45 14 * * 1-5  /opt/quant/deploy/run_reminder.sh pre
55 14 * * 1-5  /opt/quant/deploy/run_reminder.sh same_day_warn
2  15 * * 1-5  /opt/quant/deploy/run_reminder.sh same_day_close
10 15 * * 1-5  /opt/quant/deploy/run_reminder.sh same_day_closed
15 9  * * 1-5  /opt/quant/deploy/run_reminder.sh next_open_warn
25 9  * * 1-5  /opt/quant/deploy/run_reminder.sh next_open_final
35 9  * * 1-5  /opt/quant/deploy/run_reminder.sh expired
```

`run_reminder.sh` 只做三件事：检查交易日、检查 ticket 状态、调用 `notify`；不生成信号、不改账户。14:50 的初始通知由 `run_daily.sh`/`live_signal` 发送，提醒脚本从 14:55 开始只做升级，避免和信号生成抢跑。

## 7. 网页交互

### 7.1 首屏

首屏只回答一个问题：**现在要我做什么？**

- 有 PENDING：大卡片“需要你执行”，倒计时到下一个 deadline，订单票 + 按钮。
- 有 PARTIAL：显示未完成腿，按钮“补登剩余成交”。
- 有 EXPIRED_UNRESOLVED：红色“已错过两个窗口”，按钮“补登实际成交/标记未交易”。
- 无票：显示“今天没有待执行信号”，以及下一次检查日。

### 7.2 按钮行为

| 按钮 | 行为 | 必填 |
| --- | --- | --- |
| 已按计划成交 | 预填实际份额/价格/费用，用户核对后提交 | 实际价格、费用、证据勾选 |
| 部分成交 | 逐腿登记已成交份额，剩余保留 PENDING | 份额、价格、费用 |
| 未成交/跳过 | 选择原因：忘记/不想交易/市场异常/其他 | 原因可选但建议必填 |
| 10 分钟后再提醒 | 最多 2 次；不能跨过窗口截止 | — |
| 复制卖出指令 | 复制“518880 卖出 10900 份 限价 7.90–7.97” | — |
| 复制买入指令 | 复制“501018 买入 43300 份 限价 2.25–2.29” | — |

### 7.3 防误触

- 确认按钮需要二次确认（“已核对交割单”勾选）。
- 确认后展示“已登记事实，未下单”提示。
- 不允许网页直接触发券商下单。
- 确认/跳过使用幂等键，重复点击不重复记账。

## 9. 数据与健康检查

### 9.1 生成 ticket 前的前置检查

- 当天是交易日（`is_trading_day`）；
- 数据日期 = 上一完整交易日；
- 8 只标的都有当日数据；
- 实时/收盘价有效；
- 池版本、策略 identity、config hash 一致；
- 无未决 ticket（有则提示先处理）。

任何一项失败：`BLOCKED`，Bark 异常告警，不生成 ticket。

### 9.2 运行时健康

- `trade-web` active；
- Bark key 存在且最近一次推送成功；
- cron 三任务存在；
- 数据新鲜度；
- `state.json` 可读写、属主正确（quant:quant）。

复用 `deploy/health_check.sh`，新增“提醒任务”“ticket 年龄”“Bark 失败日志”三项。

## 10. 安全与合规

- 不接券商、不存券商密码/验证码、不做 RPA。
- 网页继续使用密码 + token；HTTPS。
- ticket 不含账号、身份证、完整资金账号。
- 确认接口要求“已核对交割单”勾选。
- 所有状态变化写入 `status_history`，append-only。
- 通知内容不包含 secret；Bark key 只在 config/env。
- 单用户系统，不做多租户。

## 11. 指标与复盘

| 指标 | 定义 | 目标 |
| --- | --- | --- |
| `missed_rate` | 进入 EXPIRED_UNRESOLVED 的 ticket / 总 ticket | < 5% |
| `signal_to_action` | 信号生成到确认/跳过的中位时长 | < 10 分钟 |
| `same_day_rate` | 同日窗口完成的比例 | 监控 |
| `next_open_rate` | 次日开盘完成的比例 | 监控 |
| `reminder_delivery` | Bark 成功 / 尝试 | > 99% |
| `slippage_bps` | 实际成交价 vs ticket 参考价 | 监控 |
| `adherence` | 按票执行 / 总信号 | 监控 |
| `model_vs_actual` | 模型组合 vs 实际账户收益差 | 周报 |

每周生成“执行复盘”：

- 本周信号数、执行数、跳过数、漏单数；
- 漏单原因分布；
- 平均滑点；
- 如果全部执行，模型收益 vs 实际收益差；
- 下周改进项。

## 12. 失败模式与处理

| 失败 | 处理 |
| --- | --- |
| 服务器/cron 挂 | 外部 uptime 监控 + health_check + Bark 告警；不生成假票 |
| Bark 失败 | 重试 3 次 + 邮件/备用 webhook + 网页 banner |
| 数据过期/缺行 | `BLOCKED`，不发可执行票；Bark 告警 |
| 用户手机没网 | 多时间点 + 多通道；网页可补看 |
| 重复 cron | `dedupe_key` 去重；ticket 幂等 |
| 重复确认 | 幂等键；重复请求返回已记录 |
| 部分成交 | `PARTIAL`，剩余腿继续提醒；不伪造全部成交 |
| 价格跳空/限价未成交 | 用户选择跳过/改价；记录滑点 |
| 旧 ticket 未决 + 新信号 | 阻塞新票，提示先处理旧票；不自动覆盖 |
| 时区/节假日 | Asia/Shanghai + 交易日历；非交易日不发 |
| 账户状态与 ticket 不一致 | 确认时校验持仓/现金；不一致要求人工核对 |
| 网页 token 过期 | 重新登录；Bark 链接带登录跳转 |

## 13. 实施阶段

### Phase 1（MVP，1–2 天）
- `remind_pending.py` + `run_reminder.sh`；
- 14:45/14:55/15:02/15:10 四个提醒；
- ticket 数据结构 additive；
- 网页首屏 ticket 卡 + 倒计时 + 复制指令；
- 确认/跳过沿用现有接口，补幂等；
- 单测 + 服务器 dry-run。

### Phase 2（次日窗口，2–3 天）
- 09:15/09:25/09:35 提醒；
- snooze（最多 2 次）；
- 跳过原因、通知日志、Bark 失败 fallback；
- `EXPIRED_UNRESOLVED` 状态与阻塞逻辑。

### Phase 3（对账与复盘，3–5 天）
- `PARTIAL` 部分成交；
- 滑点/执行率/漏单周报；
- 模型组合 vs 实际账户；
- 管理页测试提醒。

### Phase 4（可选，未来）
- 若拿到 QMT/PTrade：新增 broker adapter；
- 复用同一 ticket/state machine；
- 仍然默认 `ALLOW_LIVE_TRADING=false`，模拟盘先行。

## 14. 验收标准

1. 交易日 14:50 生成且只生成一张 ticket；重复运行不重复。
2. 14:45/14:50/14:55/15:02/15:10 提醒按矩阵发送；确认/跳过后立即停止。
3. 同日未处理，次日 09:15/09:25/09:35 继续提醒；09:35 后转 `EXPIRED_UNRESOLVED`。
4. 确认/跳过/部分成交均幂等；重复点击不重复记账。
5. 数据过期/缺行/服务异常时不生成 ticket，只发异常告警。
6. ticket 首屏手机 30 秒内可完成“复制指令 + 确认/跳过”。
7. 所有状态变化有 `status_history`；周报能算出漏单率、滑点、执行率。
8. 不接券商、不存密码、不做 RPA；`ALLOW_LIVE_TRADING=false` 不变。
9. 旧 pending/旧确认接口兼容；回滚到旧版不影响账户状态。

| --- | --- | --- |
| 同日提醒时间 | 14:45 / 14:50 / 14:55 / 15:02 / 15:10 | 是 |
| 次日提醒时间 | 09:15 / 09:25 / 09:35 | 是 |
| 主要通道 | Bark | 可加邮件/企业微信 |

## 16. 结论

半自动的“极致”不是更多通知，而是：

- 每个信号有票、有窗口、有 deadline；
- 每个动作有状态、有幂等、有审计；
- 每个漏单有终态、有原因、有复盘；
- 系统只准备和执行对账，不碰券商、不替用户下单。

这套设计可以在现有 V5 信号、Bark、网页确认、pending/state 基础上增量实现，不需要 broker API，也不需要改动策略参数。
